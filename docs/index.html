Built for the person in the loop.

Four ideas, grouped in fours by design

A flow you can predict

The same skeleton every time, so you know what comes next.

  • Four phases in eight steps: ① Define → ② Plan → ③ Build → ④ Accept, with a gate at the end of each phase.
  • Four levels with separate jobs: L1 orchestration, L2 design and judging, L3 work, L4 tools, MCP, hooks and rules.
  • Three profiles, general, research and dev, adapt the same skeleton to the kind of work.
  • Optional model presets per profile set each agent's model and effort, so you can pick a lighter or a stronger setup for the task.

Source: plugins/my-agent/skills/my-agent/SKILL.md, plugins/my-agent/docs/build-guide/my-agent-architecture.md, README.md

Less load on you

Questions are few, short and hard to miss.

  • Every question is an AskUserQuestion popup with 2 to 4 choices, the recommended one first, so nothing gets lost in the chat.
  • The scope and plan reports open with an Overview (background and goal) and a Takeaway, then a table of 5 to 8 rows; the details are in the monitor's Report tab.
  • The structure comes in groups of about four (Cowan's 4±1 working-memory limit), so a person can hold it at a glance.
  • Delegated approval (--auto) answers routine popups with the recommended choice; G2, G3 and E still come to you. The recommended permission mode is auto, with the ask and deny rules and the hooks still in force.

Source: plugins/my-agent/skills/my-agent/SKILL.md, plugins/my-agent/docs/build-guide/my-agent-architecture.md, plugins/my-agent/l4-tools-guards/permissions/permissions.json

Checked by someone else

The agent that made the work does not judge it.

  • Plan review, verification and review are separate subagents with their own context; the author's explanation is not passed along.
  • Hooks enforce the key rules in code: before plan approval, delegation is denied and writes outside the task folder are asked; delivery without a fresh verdict is blocked and a stale commit is asked; each agent has a read and write scope.
  • Work can run in a git worktree under .claude/worktrees/ instead of the main tree: a task worktree on its own branch, and the first parallel group of coders in dev.

Source: plugins/my-agent/l1-orchestration/phases/plan.md, plugins/my-agent/l1-orchestration/phases/accept.md, plugins/my-agent/l4-tools-guards/hooks/hooks.json, plugins/my-agent/skills/my-agent/SKILL.md, plugins/my-agent/l1-orchestration/profiles/dev.md

Easy to look after

Every task leaves a trail you can read later.

  • A read-only local monitor shows each task as it runs; its Report tab puts one task on one page, with the phase timeline, the gate marks and the G3 wait.
  • run-log records phases, popups and subagent calls with the model, tokens and time; the retrospective tallies gate decisions and cost per stretch.
  • Improvements pile up in a feedback list, each marked with its level, L1 to L4.
  • In dev, the coder writes the tests first, and the commit carries the code with its tests.

Source: plugins/my-agent/monitor/README.md, plugins/my-agent/l4-tools-guards/scripts/run-log.py, plugins/my-agent/l4-tools-guards/scripts/gate-report.py, plugins/my-agent/l4-tools-guards/scripts/feedback.py, plugins/my-agent/l3-workers/agents/coder.md

Human in the loop

Decisions come to you at fixed gates.

my-agent stops at set points, shows a short report in the chat and asks by popup. At plan approval it pastes the whole mock-up of the deliverable; when the result has to be seen to be judged, like a screen, a prototype HTML file can be opened in the browser first.

G1aScope: what will and will not be doneConfirm / edit / stop
G1bPlan: the work units and the mock-upApprove / request changes / stop
G3Result: the deliverable and where it goesAccept / rework / stop
